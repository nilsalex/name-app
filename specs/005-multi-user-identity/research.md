# Research: Multi-User Identity (005)

Date: 2026-11-02. Resolves the technology choices for replacing the A/B
alias mapping with opaque internal user IDs. Constraints per constitution:
toy app, small user count (now extensible), simplicity paramount, free-plan
only, no new dependencies.

## R1: What do the internal user IDs look like?

**Decision**: 128 bits of `node:crypto.randomBytes`, base64url-encoded →
22-character opaque string (e.g. `QkT9x2mR7pLw4vNs8JeD1A`). Generated by the
app at first sign-in; never derived from the email; no prefix/semantics.

**Rationale**: Meets FR-004 exactly — app-generated, non-enumerable
(128-bit entropy makes guessing impossible), stable once stored. Base64url
is URL/Redis/cookie-safe without escaping. `randomUUID()` was rejected only
because its 36-char form with dashes is no safer and slightly less compact;
the type is the same idea. No ID library needed (Principle V).

**Alternatives considered**:
- *UUID v4 (`crypto.randomUUID()`)* — equally valid; longer, dashed. Rejected
  for compactness only; if adopted later, existing IDs remain valid (opaque
  strings, no format contract).
- *Sequential integer IDs* — enumerable (a signed-out visitor could probe
  how many users exist); fails FR-004's opacity requirement. Rejected.
- *Email hash (HMAC of address)* — deterministic from the email, i.e.
  email-derived; violates the clarified decision "NOT from mapping email
  addresses" and FR-012 (no personal info embedded in identifiers).
  Rejected.

## R2: Where are user records stored, and what is in them?

**Decision**: A single Redis hash `namewahl:users` mapping
`lowercased email → JSON record`:

```json
{ "id": "<22-char opaque id>", "num": 3, "createdAt": "2026-11-02T10:00:00.000Z" }
```

- `id`: internal user ID (R1) — the only identifier that ever reaches vote
  records or the session.
- `num`: sequential display number (1, 2, 3, …) assigned at first sign-in
  from a counter key `namewahl:users:nextnum` (INCR). Powers the neutral
  "Person 3" label (FR-008) without storing any personal data.
- `createdAt`: ISO timestamp, for operator debugging only; never displayed.

Access via a read-or-create on sign-in (R3). The email is the hash field
*only because it is the lookup key at sign-in time*; it never appears in
vote records, sessions, or the UI (FR-008/FR-012 — stored identifiers are
IDs, not emails).

**Rationale**: One flat hash is the smallest persistent store that makes IDs
stable across sign-ins and devices without a schema. Redis hashes are
native to the existing Upstash client; the record is two scalars + a
timestamp. Free-plan impact: one HGETALL per sign-in, one HSET + one INCR
only at first sign-in.

**Alternatives considered**:
- *Store user records only in env config* — env vars cannot mint stable
  random IDs at runtime; every redeploy would remap identities. Rejected.
- *A separate key per user (`namewahl:user:<id>`)* — N keys instead of 1,
  and lookup by email still needs a second index. Rejected.
- *Redis JSON / lists* — no benefit over a hash at this scale. Rejected.

## R3: How does sign-in resolve an email to a user ID?

**Decision**: After `verifyGoogleIdToken` succeeds and the address is
approved (R4), `resolveUser(email)` runs:

1. `HGET namewahl:users <normalized email>` → existing record → reuse `id`.
2. Miss → generate ID (R1), `INCR namewahl:users:nextnum`, `HSET` the new
   record, return it.
3. Race safety: two simultaneous first sign-ins could both INCR; the loser
   overwrites via HSET with its own ID — both are valid app-generated IDs,
   and the display number is cosmetic. Acceptable for a toy app; documented
   in data-model.md rather than solved with WATCH/Lua.

The session is then sealed with `{ uid, iat }`.

**Rationale**: Sign-in is the only place identity is resolved; votes and
page renders read only the session. One extra round trip per sign-in is
invisible at this scale.

**Alternatives considered**:
- *Deterministic ID from HMAC(email, secret)* — no store needed at all, but
  is email-derived (violates the core decision; see R1). Rejected.
- *Lua script for atomic read-or-create* — strictly correct but adds
  complexity for a race that only affects a cosmetic display number.
  Rejected (Principle V).

## R4: How does the approved list work now?

**Decision**: One comma-separated secret env var `APPROVED_EMAILS`, e.g.
`APPROVED_EMAILS=person.a@gmail.com, person.b@gmail.com`. Parsed once per
access: split on commas, trim, lowercase, drop empties, dedupe. An approved
address not yet in `namewahl:users` gets a new user record at first sign-in
(R3); removing an address from the list blocks *future* sign-ins but leaves
existing records and data untouched. Adding an address = editing one env
var + redeploy — no code, no migration (FR-011, SC-006).

**Rationale**: Directly satisfies FR-011 ("extendable without code changes
or data migration") which two per-alias variables cannot do. Replaces 004's
`APPROVED_USER_A_EMAIL`/`APPROVED_USER_B_EMAIL`; the alias→A/B mapping
disappears entirely (the clarified core of this feature).

**Alternatives considered**:
- *Keep two per-alias vars and add a third, fourth…* — unbounded variable
  zoo; alias suffix no longer meaningful. Rejected.
- *Committed JSON config* — secrets must never be committed. Rejected.
- *Manage the list in Redis* — requires an admin UI or manual redis-cli;
  env vars are where the other secrets already live. Rejected.

## R5: What changes in the session, and how do legacy records coexist?

**Decision**: Session payload changes from `{ alias: "A" | "B", iat }` to
`{ uid: string, iat: number }`; `verifySession` accepts any non-empty
opaque string UID (format check: 1–64 chars of base64url). Existing 004
sessions become invalid after deploy (users re-login once — acceptable, and
the only migration). `VoteRecord.user` widens from `"A" | "B"` to `string`;
legacy stream entries with `user: "A"` / `"B"` are passed through verbatim —
ranking and winners logic reads the `user` field only for per-user views,
which don't exist yet, so mixed values render fine by construction.

**Rationale**: Widening a string field is the least-change path; no data
migration, no stream rewrite (SC-006). Re-login after deploy is the
documented cost of invalidating alias-carrying sessions.

**Alternatives considered**:
- *Keep alias field alongside uid* — two identity schemes in one session;
  ambiguity about which wins. Rejected.
- *Batch-migrate historical vote records to new IDs* — rewrites history and
  mapping "A"→which new user is unknowable (both new users are new
  identities per spec edge case: no automatic merging). Rejected.

## R6: How are users displayed now ("Person 1", …)?

**Decision**: Display label = `Person ${num}` from the user record, resolved
at sign-in and passed to `VoteClient` as a prop (`label: string`). The hint
line becomes "Welcher Name gefällt dir besser, Person 3?". Ranking/winners
pages stay alias-agnostic (they aggregate by name, not by voter) and remain
untouched.

**Rationale**: FR-008 allows neutral labels; `num` is assigned at first
sign-in and stable. No email ever surfaces (FR-012).

**Alternatives considered**:
- *No label at all* — slightly colder UX, but zero surface. Kept as fallback
  if `num` is missing (label "Person"). Rejected as primary (SC-001 promises
  the user sees *their* identity).
- *Let users pick a nickname* — new input surface, out of scope. Rejected.

## R7: What happens on sign-out and for non-approved accounts?

**Decision**: Unchanged from 004: `signOut` deletes the cookie; a verified
Google address not on `APPROVED_EMAILS` gets the friendly denial
("Diese Adresse ist nicht freigeschaltet.") with no session and no record
created. Denial does NOT create a user record — only approved sign-ins do.

**Rationale**: FR-003 semantics are orthogonal to the ID scheme; no rework
needed from 004's implementation.

**Alternatives considered**: None with materially different outcomes.

## R8: Testing strategy without Google/Upstash credentials?

**Decision**:
- `lib/user-ids.ts`: pure — tests assert format (22 base64url chars),
  uniqueness across N generations, and independence from input email.
- `lib/users.ts` (rewrite): pure parsing — accepts an `env` record; tests
  cover trim/case/dedupe/empties, single-address list, malformed (empty)
  list → fail-fast error.
- `lib/user-store.ts`: resolution logic parameterized by a tiny
  `UserStore` interface (`get`, `set`, `nextNumber`) → unit tests use an
  in-memory map: first resolution creates, second reuses, display numbers
  increment, normalized-email keying, no record for unapproved emails.
- `lib/session.ts`: updated payload tests (uid round-trip, tamper, expiry,
  legacy `{alias}`-shaped payload rejected).
- Integration: the existing `submit-auth` test now also asserts a
  `signOut`-shaped (cookie-less) environment writes nothing — logic
  unchanged, only re-validated against the new session shape.

Live Google/Upstash flows stay in quickstart.md (user's environment), same
as 003/004.

**Rationale**: Matches constitution Principle III/IV and the established
test idioms; no new test infrastructure.

**Alternatives considered**: Real-Upstash integration test for the users
hash — credentials absent in this environment; deferred to quickstart V2/V3.
Rejected for CI here.
